# HH.ru contracts — live reconnaissance

Дата наблюдения: 2026-07-15 (Asia/Ho_Chi_Minh)
Сайт: https://hh.ru/
Роль: авторизованный соискатель

## Состояние сессии

Вход выполнен вручную пользователем в Codex In-app Browser. Признаки активной сессии: в шапке отображаются «Чаты», «Избранное», «Уведомления», «Создать резюме»; главная страница показывает «Отклики 698» и «Просмотры +701».

Сессию нельзя безопасно экспортировать в файлы или читать через cookies/localStorage. Вкладка оставлена живой; браузерный профиль должен сохранять состояние между продолжениями, но это нужно перепроверить при следующем запуске.

| Назначение | URL | Наблюденный контракт |

## Контракты данных, видимые в DOM

### Карточка вакансии

- ссылка: `/vacancy/<id>`;
- название вакансии — текст ссылки;
- работодатель: `/employer/<id>`;
- зарплата — отдельный текстовый блок, может отсутствовать;
- опыт (`Опыт 1-3 года`, `3-6 лет`, `более 6 лет`);
- удалённость: `Можно удалённо`;
- график/выплаты/локация — опциональные текстовые блоки;
- действия: `Откликнуться`, `Добавить в избранное`, `Скрыть`, иногда `Связаться`;
- дополнительные признаки: рейтинг, число отзывов, метро, «Сейчас смотрят N человек».

### Резюме

На наблюдаемом аккаунте два резюме:

- `Backend-разработчик` — ссылка поиска содержит `resume=da8df5aeff0f1da9b30039ed1f48564e49664a`;
- `Python разработчик` — ссылка поиска содержит `resume=65d434cbff0edda4700039ed1f5750474e3866`.

Наличие/форма резюме определяется не URL вида `/resume/<id>`, а списком на `/applicant/resumes` и ссылками `search/vacancy?resume=...`.

### Отклики

Строка отклика может содержать статус (`Отказ`, `Не просмотрен`), название вакансии, работодателя, дату, ссылку работодателя и действия `Перейти в чат`, `Усилить отклик`. Это отдельный runtime-контракт, не равный успешному отклику.

## Сопоставление с расширением

Уже покрыто текущим кодом:

- allowlist `hh.ru` и `*.hh.ru` в `manifest.json`;
- `/applicant/resumes`, `/resume/`, `/vacancy/` в `src/live/resumeDetector.ts`;
- `/search/vacancy` и `page=` в `src/live/searchPagination.ts`;
- карточки `/vacancy/` в `src/live/searchResultsParser.ts`, `src/content/live-mode-content.ts` и `src/background/service-worker.ts`;
- API/backend путь получения резюме в `BackendHTTPClient.getMyResumes()`;
- backend/live engines и controlled acquisition в `src/runtime/`.

Реальные расхождения/риски:

1. URL чатов нельзя выводить по имени кнопки: прямой `/applicant/chats` дал 404. Нужно один раз снять фактический href/маршрут кликом по «Чаты».
2. Резюме на UI представлены хешами в query-параметре `resume`, поэтому fallback по ссылкам `/resume/` необходим.
3. В карточках используются вложенные кнопки и ссылки; парсер должен выбирать ближайший контейнер карточки, а не глобальный текст.
4. Статусы откликов и действия чата являются отдельным контуром от подачи отклика; нельзя считать наличие кнопки «Перейти в чат» успехом apply.
5. HH добавляет `hhtmFrom`, `from`, `hhtmFromLabel` и рекламные query-параметры. Идентификацию нужно делать по pathname и ключевым параметрам, игнорируя tracking-параметры.

## Следующий проход

Нужно продолжить с авторизованной вкладки:

1. кликнуть фактическую кнопку «Чаты» и сохранить URL/DOM;
2. открыть одну вакансию и зафиксировать apply-flow: обычный отклик, cover letter, уже откликался, редирект/login;
3. открыть профильное меню и снять ссылки редактирования резюме/настроек;
4. открыть автопоиски и снять форму создания/редактирования только чтением;
5. снять фактическую пагинацию и query-параметры поиска для разных фильтров.

Не выполнялись: отправка откликов, сообщения работодателям, изменение резюме, избранного или настроек.

## Контрактная заметка для реализации

Скрейперу/расширению нужно различать:

```text
page route
  -> page state (authenticated / empty / populated / 404)
  -> repeated entity cards
  -> entity links (/vacancy/id, /employer/id, /search/vacancy?...)
  -> action labels
  -> side-effect class (read-only, favorite, delete, apply, chat, settings)
```

Кнопки `Откликнуться`, `Перейти в чат`, `Удалить`, `Усилить отклик`, `Поднять в поиске`, `Настроить мессенджер` нельзя считать взаимозаменяемыми: они относятся к разным доменным операциям и требуют отдельной классификации.
